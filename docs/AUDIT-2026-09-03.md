# Fibott Backend Audit — 2026-09-03

Scope: everything outside the recognition pipeline (which was already fixed this session — real
TFLite Micro inference on the ESP32, network-blocking gate fix, QVGA capture). This covers auth,
points, deposits, kiosk sessions, vouchers, and the MikroTik integration.

`docs/STATUS.md` marks almost everything "Verified" on the strength of `npm run lint`, `npx tsc
--noEmit`, and `npm run build` passing. Those checks catch syntax and type errors, not business-logic
bugs — the same way the ESP32 firmware's fake classifier compiled cleanly while doing nothing real.
Four focused passes over the actual route/lib code turned up real issues, several of them currently
exploitable as the app is configured today. Ordered most severe first, grouped by area.

---

## 0. Directly relevant to the recognition fix you just made

**The ESP32 now makes the correct accept/reject decision on-device — but the database and the
customer's points still come from the OLD, weaker cloud classifier, not the ESP32's decision.**

- `src/app/api/device/deposit-image/route.ts` + `src/lib/classifier.ts` — the ESP32 never sends
  its own `materialType` to `/api/device/deposit-image`, only the image. That route re-classifies the
  same frame using `classifier.ts`, which defaults to the **zero-shot MobileNet + ImageNet-keyword**
  path (`FIBOTT_ML_MODE` isn't set in your env files) — the same "milk can" proxy-guessing approach
  `docs/ml.md` already flags as unreliable for cans. If it disagrees with the ESP32's real model, the
  customer is credited points for the *wrong material*, silently.
- `src/lib/deposit.ts` — `uploadImage()` fires before `sendFastScanResult()`. The first call's
  `processDeposit()` marks the session `COMPLETED` using the cloud classifier's (weaker) answer. The
  second call, carrying the ESP32's *correct* materialType, arrives to find the session no longer
  `ACTIVE` and gets written as a second, orphaned `Deposit` row: `userId: null`, `status: REJECTED`,
  reason `NO_ACTIVE_SESSION`. **Every accepted deposit writes two DB rows** — the points-earning one
  (weaker model) and a phantom rejection (discarding the ESP32's correct call). This will show up as
  confusing "rejected, no session" noise in Admin Deposit History for deposits that actually succeeded.
- `classifier.ts`'s confidence floor (`MIN_CONFIDENCE = 0.15`, meant to force `REJECTED` on
  low-confidence guesses) only applies inside the `experimental_head` mode, which isn't active. In the
  live zero-shot path there's no floor — it always coerces to PET_BOTTLE or ALUMINUM_CAN via a color
  heuristic, so a bad guess never gets caught.

**Why this matters for what you asked about today:** the firmware fix makes the *physical* gate
decision accurate. This bug means the *recorded* decision — what the customer's points reflect, what
shows up in admin history — can still be wrong or duplicated, independent of how good the on-device
model is. Fixing the recognition pipeline without also fixing this leaves a gap between "what happened
at the kiosk" and "what the app says happened."

**Direction:** have the ESP32 send its own `materialType` (it already computes it) to
`deposit-image`/`scan` as the authoritative signal, treat the cloud classifier's opinion as
telemetry/disagreement-logging only (a "compare" mode already exists in `classifier.ts:357-381` for
exactly this, it's just not wired to the path that matters), and make session-completion atomic so a
second call for the same session can't create an orphaned row.

## 1. Critical — exploitable or actively broken today

**Account pre-hijacking via unverified registration + auto-linking**
`src/app/api/auth/register/route.ts`, `src/lib/auth.ts`
Registration marks the email verified immediately — no ownership proof is ever collected, and the
verification-email code path exists but is never called. Combined with `allowDangerousEmailAccountLinking:
true` on the Google provider, anyone can register `victim@gmail.com` with a password of their choosing;
when the real victim later signs in with Google, NextAuth links their Google identity onto the
attacker's existing row. The attacker keeps standing access to that account (points balance, vouchers,
profile) indefinitely.

**Voucher codes disclosed to anyone, unauthenticated, right now**
`src/app/api/mikrotik/sync/route.ts`
The route fails *open* if `MIKROTIK_SYNC_KEY` is unset — and it isn't set in either `.env` or
`.env.local` in this checkout. Even with a key set, the endpoint returns the plaintext code of the
oldest pending voucher system-wide, and that code is both the HotSpot username *and* password (with
`shared-users=1`, so redeeming it locks the real owner out). Anyone who finds this URL can currently
harvest and redeem other users' paid-for WiFi time.

**Double point awards when the firmware's two upload calls race**
`src/lib/deposit.ts`
Session completion is a plain `update`, not a conditional `updateMany({where:{status:"ACTIVE"}})`. Two
concurrent requests for the same session (exactly what `uploadImage()` + `sendFastScanResult()`
produce for every accepted item, or any retried upload) can both pass the "is this session active"
check before either commits, both award points, both create an ACCEPTED deposit row.

**Suspending a user doesn't actually stop them**
`src/lib/auth.ts`, `src/proxy.ts`, and every protected route checked (`vouchers/redeem`,
`deposit-sessions`, `user/password`, `user/profile`)
JWT sessions carry a `status` field that's refreshed from the DB on every request but never checked
anywhere. An admin suspending an abusive account doesn't block their existing session — they can keep
redeeming vouchers and starting deposit sessions until the JWT itself expires.

## 2. High

- **Deposit completion never checks device ownership** (`deposit.ts`) — despite `kiosk/session/route.ts`
  atomically binding a session to one device, `processDeposit()` never verifies the calling device
  matches. Any device with a valid API key that learns a `sessionId` can submit deposits against a
  session bound to a different physical kiosk — this compounds the double-award bug above.
- **Live legacy session-claim endpoints bypass ownership entirely**
  (`src/app/api/device/sessions/claim/route.ts` and siblings) — grabs the oldest pending session
  system-wide for any device with a `KIOSK_CONTROLLER` key, no code/user match. These appear to be
  dead for real traffic (the canonical flow never puts a session in `PENDING`) but are still live,
  reachable endpoints.
- **MikroTik sync has head-of-line blocking** (`mikrotik/sync/route.ts`) — always returns the single
  oldest pending voucher; if RouterOS creates the HotSpot user but the confirm call fails, that voucher
  is stuck forever and **blocks every other user's voucher** from syncing behind it, with no retry cap.
- **A lost REST response can double-create HotSpot users** (`vouchers/redeem/route.ts`,
  `mikrotik-client.ts`) — a timeout is treated as "never happened" and a new code is queued via
  outbound sync, even though the original request may have already succeeded server-side.
- **Admin password reset falls back to a hardcoded default** (`"Fibott2026!"` in
  `admin/users/reset-password/route.ts`), with no forced rotation — a durable, guessable backdoor into
  any account that's ever been reset.

---

## 3. Medium

- Two starting sessions on the same kiosk in the same instant both pass the "is it busy" check
  (`kiosk/session/route.ts`) — no unique constraint backs it, so one gets orphaned.
- No DB constraint limits a session to one accepted deposit (`prisma/schema.prisma`) — the missing
  backstop behind the double-award bug above.
- Points spent on a voucher that gets stuck `PENDING` are never automatically refunded or expired
  (`voucher.ts`).
- `MIKROTIK_SYNC_KEY` travels as a URL query param on every 3-second poll (landing in access logs),
  compared with `===` instead of a timing-safe check, and is hardcoded in cleartext in
  `infra/fibott-sync.rsc`, which isn't excluded by `.gitignore`.
- `trustHost: true` with no canonical-origin pinning in `auth.ts` — risk depends on your reverse-proxy
  setup, worth checking `Host`/`X-Forwarded-Host` handling.

---

## 4. Low

- Password-reset tokens aren't invalidated when a new one is requested (`tokens.ts`) — old links stay
  live for their full hour.
- Admin reset accepts a 6-character password minimum vs. 8 everywhere else.
- Kiosk session `code` field is a raw millisecond timestamp — predictable, though not used for lookup
  in the canonical path.
- Voucher's placeholder `code` (`PENDING-${Date.now()}`) can collide under concurrency against a
  unique column, throwing instead of failing gracefully.
- RouterOS integration falls back to full `admin` credentials instead of a least-privilege API user.
- `scan/route.ts` and the old cloud-classifier confidence floor are effectively dead code given the
  ESP32 now decides locally — worth simplifying once the section 0 fix lands, rather than leaving two
  competing "who decides" code paths around.

---

## What's actually solid

Worth naming, since not everything here is bad news: `spendPoints` correctly folds the balance check
into the update itself (no race there), voucher code generation uses real crypto-random bytes with
good entropy, voucher creation and points-spend are wrapped in one transaction, `device-auth.ts`'s
bcrypt-based API key check is timing-safe and correctly rejects inactive devices, and
`MIKROTIK_INSECURE_TLS` defaults to verified TLS rather than failing open.
